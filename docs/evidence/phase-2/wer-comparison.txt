Why run 1 cannot show parity (two differences the gate is not about)
1. Different chunkers. whisper-cli's side was cut by the harness's VAD step, the engine's by its own chunker; they cut at different pauses in 2 of the 5 utterances that differed (fleurs-hi 33253568: 11,400 ms against 11,295 ms; fleurs-ur 64116877: 8,785 ms against 14,260 ms).
2. whisper-cli's corrupted --prompt. The harness passes the previous chunk's text to whisper-cli as a `--prompt` command-line argument. On Windows whisper-cli reads its command line in the ANSI code page, which turns every Devanagari or Arabic-script character of the prompt into "?". The model is then prompted with garbage and some chunks come out as "??? ??? ???" (fleurs-hi 10798430, second chunk: same chunk boundaries on both sides, 12 correct words from the engine). Shown on that chunk (not committed): no prompt gives correct Devanagari, an ASCII prompt gives correct Devanagari, a Devanagari prompt gives "??? ??? ??? ...". All output modes (stdout, -oj, -ojf, -otxt) give the same "???", so it is not an output-reading problem and not a split character in the output. The engine passes the context through the library, in UTF-8.
   My first explanation in this file (a character split across segments in whisper-cli's JSON output) was wrong; the prompt is the cause.

Run 2 (the parity measurement) removes both: whisper-cli decodes the exact chunks wb-engine cuts, and previous-text context is off on both sides (whisper-cli cannot carry it for non-Latin text on Windows). English with context on, on the same chunks, also matches (20 of 20 identical; information in wer-parity.txt).

Consequence for Phase 5a numbers: docs/GATES.md (5a rows) and docs/evidence/phase-5a/tables-phase-5a.md now say that every 5a whisper-cli run with context (rolling, night) on Hindi, Urdu or CoSHE-Eval used the corrupted prompt, and Phase 5 scores every model through `wb-engine batch`.
