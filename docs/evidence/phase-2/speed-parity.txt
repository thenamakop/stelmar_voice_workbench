Reading the result (10 Nov 2026)
- Speed: the engine is within 1% of whisper-cli on processing time (+0.4%) and on the whole process (+0.9%); model load is +4.3% (about 0.1 s of 1.4 s). No clip is over 10% on any of the three timings, so there is no gap to explain. The 15.7 s against 13.6 s seen earlier on one clip was the unoptimised first build (before /O2) and an engine with flash attention off; neither applies to these builds.
- A first run of this script gave the wrong picture for Hindi (the engine looked 40 to 75% slower): the script had left out the language flag, so whisper-cli decoded Hindi audio as English. The harness always passes -l; the script now does too. That run is not evidence.
- Text: 3 of 6 clips differ by 2 or 3 words (rare-word spelling). Each side gives the same text on every repeat (3 runs each), so this is not randomness. whisper-cli decodes the whole clip including its leading and trailing silence, the engine only the VAD chunk. Checked on fleurs-en/12596571: whisper-cli given exactly the engine's chunk (630 to 6760 ms) returns the engine's text word for word. The 3-WER comparison cuts chunks for both sides with the harness's VAD step, so this effect is part of what that comparison measures.
- OpenMP: whisper-cli is built with OpenMP, the engine without (ggml's own thread pool, no extra runtime DLL to ship). At 8 threads on this machine it makes no measurable difference. Not tested on the laptops (Speed table rows use the engine only).
- Both builds: whisper.cpp v1.9.5 commit d1be6fde11ac, portable AVX2 (GGML_NATIVE=OFF); engine tree hash e736b4c9a5be.
